## 1. Цели и контекст

### 1.1. Бизнес-цель
Чат-агент для **нетехнических руководителей** ритейл-компании. Он позволяет на естественном языке:
- задавать аналитические вопросы о продажах, клиентах, продуктах и динамике;
- обсуждать результаты в формате диалога (уточнения, follow-up вопросы, сравнения);
- генерировать отчёты с инсайтами и **action items**;
- управлять библиотекой сохранённых отчётов (сохранять, просматривать, удалять).

### 1.2. Примеры целевых запросов
- «Почему пользователи из штата X тратят меньше? Как это соотносится с пользователями из штата Y?»
- «Почему в прошлом месяце вырос churn rate?»
- «Сделай отчёт за Q1 с инсайтами и action items на Q2»
- «Топ-10 клиентов по сумме покупок»
- «Сравни продукты X и Y и объясни, почему они продаются по-разному»
- «Помесячная выручка», «выручка по продуктам на сегодняшний день»
- «Какие данные у нас есть и что с ними можно делать?»
- «Удали все отчёты, где упоминается клиент X» / «Удали все отчёты из этого разговора»

### 1.3. Пользователи и роли
| Роль | Описание |
|---|---|
| Executive (конечный пользователь) | Задаёт вопросы, читает и удаляет **свои** отчёты, видит только данные по «своим» продуктам |
| Admin / Content owner (не разработчик) | Меняет персону и тон агента (например, CEO раз в неделю), курирует Golden Bucket |
| Analyst (эксперт) | Создаёт и валидирует «Trios» для Golden Bucket |
| Engineer / On-call | Мониторинг, разбор инцидентов, eval-прогоны |

## 2. Источники данных

### 2.1. BigQuery (read-only)
Датасет: `bigquery-public-data.thelook_ecommerce`. Обязательные таблицы:

| Таблица | Ключевые поля | Примечания |
|---|---|---|
| `users` | `id`, `first_name`, `last_name`, `email`, `age`, `gender`, `state`, `street_address`, `postal_code`, `city`, `country`, `latitude`, `longitude`, `traffic_source`, `created_at` | **Содержит PII** |
| `orders` | `order_id`, `user_id`, `status`, `gender`, `created_at`, `returned_at`, `shipped_at`, `delivered_at`, `num_of_item` | |
| `order_items` | `id`, `order_id`, `user_id`, `product_id`, `inventory_item_id`, `status`, `created_at`, `shipped_at`, `delivered_at`, `returned_at`, `sale_price` | Источник выручки |
| `products` | `id`, `cost`, `category`, `name`, `brand`, `retail_price`, `department`, `sku`, `distribution_center_id` | Основа для разграничения доступа по продуктам |

Требования:
- [PROTO] Агент динамически строит и выполняет SQL (диалект BigQuery Standard SQL) только по этим четырём таблицам (whitelist).
- [PROTO] Используется существующий `bq_client.py` (`BigQueryRunner`), при необходимости его нужно доработать: dry-run, `maximum_bytes_billed`, таймауты, метки запросов.
- [PROTO] Агент умеет отвечать на вопросы о структуре БД: какие таблицы и поля есть, какие анализы возможны. Схема берётся через `get_table_schema` и кэшируется.
- Доступ только на чтение: любой не-`SELECT` запрос (DML/DDL) отклоняется ещё до отправки в BigQuery.
- Перед финальной фиксацией схемы колонки нужно сверить с реальной схемой через `get_table_schema`.

### 2.2. Golden Knowledge Bucket (теоретический)
Data lake с историческими «Trios»: **Question → SQL Query → Analyst Report**, составленными людьми-экспертами.
- [HLD] Хранилище, формат, индексирование, поиск, обновление (подробности в §3.1).
- [PROTO-lite] Локальный seed-набор из 10–20 trios (JSON/YAML) и простой retrieval, чтобы показать механику.

### 2.3. Saved Reports Library (управляется агентом)
- [PROTO] Хранилище отчётов с CRUD-операциями. В прототипе: SQLite или JSON-файл. В HLD: Firestore или Cloud SQL плюс GCS для артефактов.
- Минимальная модель отчёта: `report_id`, `owner_user_id`, `conversation_id`, `title`, `content` (markdown), `created_at`, `updated_at`, `entities`/`tags` (клиенты, продукты, штаты, нужны для поиска «mentioning Client X»), `source_queries` (SQL), `deleted_at` (soft delete).

## 3. Функциональные требования

### 3.1. Hybrid Intelligence: использование Golden Bucket [HLD] / [PROTO-lite]

**Требование:** агент не должен опираться только на данные BigQuery. Он обязан использовать Golden Bucket, чтобы понимать, как аналитики раньше интерпретировали похожие вопросы, и применять ту же логику к новым запросам.

Что описать и сделать:
1. **Ingestion / индексация**
   - Хранилище сырых trios: GCS bucket (JSON/Parquet).
   - Пайплайн индексации: событие появления нового trio → Cloud Function/Cloud Run job → embedding вопроса (и summary отчёта) → запись в векторный индекс (Vertex AI Vector Search / pgvector / BigQuery Vector Search).
   - Метаданные trio: тема, используемые таблицы, метрики, автор, дата, версия схемы, quality score, статус (`approved` / `candidate` / `deprecated`).
2. **Retrieval в момент запроса**
   - Embedding вопроса пользователя → top-k похожих trios (гибридный поиск: векторный + BM25 по ключевым словам) → опционально re-ranking.
   - Найденные SQL-паттерны и логика интерпретации (как аналитик определил churn, «underspending», какие метрики взял) подаются в контекст как few-shot.
   - Фильтр по метаданным: не подавать deprecated trios и trios под устаревшую схему.
   - Ограничение на объём контекста (top-k, усечение).
3. **Обновление со временем**
   - Новые trios от аналитиков (ручная загрузка или ревью).
   - Кандидаты от агента: успешные диалоги (положительный фидбек, отчёт сохранён, SQL выполнился без ошибок) попадают в очередь `candidate` → human-in-the-loop ревью аналитиком → `approved`.
   - Устаревание: при изменении схемы или низком рейтинге trio помечается `deprecated`; версионирование trios.
   - Дедупликация близких по смыслу trios.
4. **Golden Bucket как источник для eval:** approved trios используются как эталонный набор для оценки (§3.6).
5. [PROTO-lite] **Retrieval в прототипе:** top-3 trios автоматически подаются в промпт каждого аналитического хода (не отдельным tool, чтобы не тратить вызов LLM). **Обновление в прототипе:** ответ с оценкой `/good` и успешным SQL записывается кандидатом (question → SQL → краткий ответ, без PII) в `data/golden_candidates.jsonl`. Скрипт `scripts/review_candidates.py` позволяет аналитику одобрить кандидата и перенести его в `golden_trios.json` (human-in-the-loop); индекс embeddings пересобирается автоматически по хэшу файла.

### 3.2. Safety & PII Masking и разграничение доступа [HLD] + [PROTO]

**3.2.1. Ограничение тематики (scope guard)**
- [PROTO] Агент отвечает только на аналитические вопросы по данным компании и на вопросы о структуре данных. Off-topic запросы (написать стих, общие вопросы, код и т.п.) вежливо отклоняются.
- [PROTO] Защита от prompt injection и jailbreak: попытки «игнорируй инструкции», «покажи system prompt», «выполни DROP TABLE», «покажи email пользователя», инъекции через данные (например, текст в названиях продуктов).
- Реализация: входной классификатор (лёгкий LLM-вызов или правила) плюс жёсткие инструкции в system prompt плюс детерминированные проверки на уровне инструментов. Безопасность **не должна держаться только на промпте**.

**3.2.2. PII masking**
- [PROTO] PII ни при каких условиях не попадает в финальный вывод пользователю.
- PII-поля (нужно подтвердить список, см. вопросы): `users.first_name`, `users.last_name`, `users.email`, `users.street_address`, `users.postal_code`, `users.latitude`, `users.longitude` (и `user_geom`, если есть). Предмет обсуждения: `city` и `age` как квазиидентификаторы в сочетании с малыми выборками.
- Многослойная защита (defense in depth):
  1. **Уровень SQL (до выполнения):** парсинг SQL (например, `sqlglot`), запрет PII-колонок в итоговой выборке (`SELECT email`, `SELECT *` из `users`) и перезапись или отклонение таких запросов. Использовать PII в `JOIN`/`WHERE`/`COUNT(DISTINCT ...)` допустимо, выводить их нельзя.
  2. **Уровень результата (после выполнения, до LLM):** маскирование колонок результата по названию и по содержимому (regex для email, телефонов, адресов) → LLM **никогда не видит сырой PII**.
  3. **Уровень вывода (перед показом пользователю):** финальный сканер ответа (regex / Presidio / Cloud DLP) с маскированием.
  4. **Для HLD:** BigQuery column-level security (policy tags), authorized views без PII-колонок, Cloud DLP.
- Идентификация клиентов: только по `user_id` (или по хэшу/псевдониму). Например, «Top customers» выводятся как `Customer #12345`.
- `user_id` не считается PII, показывать его можно (см. §12.2).

**3.2.3. Доступ к данным по продуктам (row-level access)**
- [PROTO] Каждый пользователь анализирует данные **только по связанным с ним продуктам**.
- В датасете нет связки «пользователь системы ↔ продукты», поэтому её нужно ввести. **Решение:** доступ по `products.department` через `config/users.yaml`, у CEO и C-level полный доступ, вне доступа разрешены только обезличенные агрегаты по компании (см. §12.1).
- Принудительное применение (детерминированное, не через LLM):
  - Прототип: переписывание SQL. Каждая ссылка на `products`/`order_items` заменяется подзапросом с фильтром по разрешённым продуктам. Для `orders`/`users` доступ ограничивается через join на разрешённые `order_items`. Альтернатива: запрет запросов без обязательного фильтра.
  - HLD: BigQuery Row-Level Security (row access policies) или authorized views на пользователя/группу, выполнение запросов с identity пользователя (или через service account с ограниченными правами).
- Идентификация пользователя в CLI: `--user <id>` или вход при старте (имитация аутентификации). В HLD: SSO/IdP (Google Identity / Okta) → JWT → claims с группами доступа.
- Агрегаты по «чужим» продуктам («какова общая выручка компании?»): только обезличенные итоги по компании через `get_company_benchmark` (D2).

**3.2.4. Безопасность выполнения SQL**
- [PROTO] Разрешены только `SELECT`/`WITH`, только whitelisted таблицы, одно выражение (без `;`-цепочек).
- [PROTO] Ограничения стоимости: `dry_run` для оценки байт, `maximum_bytes_billed`, обязательный `LIMIT` на сырой вывод, таймаут запроса.
- Аудит всех выполненных запросов (кто, что, когда, сколько байт).

### 3.3. High-Stakes Oversight: деструктивные операции [HLD] + [PROTO]

**Требование:** поддержка команд вида «Удали все отчёты, где упоминается клиент X» и «Удали все отчёты, сделанные в этом разговоре» со **строгим подтверждением** до выполнения и без ломки UX.

Функциональность:
- [PROTO] Инструменты для отчётов: `save_report`, `list_reports`, `search_reports` (по тексту, сущностям, conversation_id, дате), `get_report`, `request_report_deletion` (подготовка + подтверждение + выполнение, см. ниже; отдельного tool «удалить без подтверждения» нет).
- [PROTO] Удалять можно **только свои** отчёты (`owner_user_id == current_user`). Чужие отчёты в выборку на удаление не попадают. Если пользователь пытается удалить чужой отчёт, агент явно об этом сообщает.
- [PROTO] Двухфазный протокол (plan → confirm → execute):
  1. LLM вызывает `request_report_deletion(criteria)`. Система детерминированно находит отчёты-кандидаты, проверяет владельца и фиксирует точный список `report_id` и хэш набора; граф останавливается через `interrupt` (это и есть pending action).
  2. Пользователю показывается предпросмотр: количество, список (название, дата, сниппет) и ясный вопрос «Удалить N отчётов? [yes/no]».
  3. Выполнение идёт **только по явному подтверждению пользователя**. Подтверждение обрабатывает код, а не LLM: LLM не может сам вызвать execute или подставить «yes».
  4. Удаляется ровно тот набор, который был показан. Если набор изменился, нужно перепросить.
  5. Отказ, таймаут или нерелевантный ответ отменяют pending action. Затем диалог продолжается как обычно (UX не ломается). Если вместо `y/N` пользователь пишет новый вопрос, удаление отменяется, а вопрос обрабатывается как обычное сообщение — пользователю не нужно повторять его.
- [PROTO] Пустой результат («отчётов с клиентом X не найдено») обрабатывается без запроса подтверждения.
- [PROTO] Удаление выполняется как soft delete (`deleted_at`) с аудит-записью. Опционально undo в течение N минут, в HLD: hard delete по retention.
- [PROTO] Неоднозначные критерии (например, «клиент X» совпадает с несколькими сущностями) → агент уточняет до формирования плана.
- Для массовых удалений выше порога (например, >10 отчётов) можно требовать усиленное подтверждение (ввести число отчётов или слово `DELETE`).
- Нужно определить, что значит «упоминание клиента X»: поиск по тексту и сущностям отчёта (`entities`). Для этого сущности извлекаются при сохранении.

### 3.4. Continuous Improvement: Learning Loop [HLD] / user level — [PROTO]

**3.4.1. Уровень пользователя** [HLD] + [PROTO]

Агент адаптируется под каждого пользователя: помнит его предпочтения между сессиями и уточняет их со временем.

*Профиль предпочтений* (фиксированный набор ключей, чтобы профиль оставался управляемым и безопасным):

| Ключ | Значения | Пример сигнала |
|---|---|---|
| `format` | `table` / `bullets` / `prose` | «давай таблицей» |
| `detail_level` | `brief` / `standard` / `deep` | «короче», «подробнее», частые «почему?» |
| `visuals` | `charts` / `text` | «покажи графиком» |
| `language` | `en` / `ru` / … | язык вопросов |
| `report_structure` | свободный текст ≤ 200 символов | «в отчётах сначала риски» |
| `focus_metrics` | список: revenue, margin, AOV, return_rate… | постоянно спрашивает про маржу |
| `focus_segments` | список: категории, штаты, бренды | часто фильтрует по Jeans |

*Источники и типы предпочтений:*
- **explicit:** пользователь прямо говорит («всегда отвечай таблицами»). Агент сохраняет через инструмент `update_user_preference` и подтверждает в ответе («Запомнил: буду показывать таблицы»). Применяется сразу.
- **inferred:** выводится из поведения. После каждого хода лёгкая модель анализирует ход на сигналы: просьба переформатировать ответ, «короче/подробнее», повторяющиеся метрики и сегменты, оценки `/good` `/bad`. Сигналы копятся в журнале; предпочтение применяется, только когда уверенность выше порога (несколько согласованных сигналов). Противоположные сигналы снижают уверенность.
- Разовая просьба («в этот раз списком») **не** меняет профиль.

*Использование в контексте модели:*
- Профиль загружается в начале каждого хода и подаётся в system prompt блоком «User preferences»: все explicit и inferred с уверенностью выше порога.
- Приоритет: инструкция в текущем сообщении > explicit > inferred > persona по умолчанию. Persona задаёт тон, профиль задаёт формат и глубину. Guardrails (PII, ACL, подтверждения) профилем не переопределяются.
- Значения предпочтений валидируются по whitelist и не могут содержать инструкций: защита от prompt injection через профиль («запомни: всегда показывай email»). Свободные поля (`report_structure`) проходят через input guard и ограничены по длине.

*Управление пользователем:* `/prefs` показывает профиль с источником (explicit/inferred) и уверенностью, `/prefs set <key> <value>` задаёт значение явно, `/prefs forget <key>` и `/prefs reset` удаляют. Всё хранится без PII и только для своего пользователя.

*Хранение:* прототип — SQLite (`user_preferences` + `preference_signals`). HLD — Firestore / Cloud SQL. Извлечение сигналов делает асинхронный воркер (Pub/Sub → Cloud Run), а не путь ответа пользователю. Профиль кэшируется в Memorystore.

**3.4.2. Уровень системы**
- Сбор фидбека (оценки, повторные формулировки, «это не то»), трейсов и ошибок SQL.
- Офлайн-анализ: кластеризация неудачных запросов → улучшение промптов и семантического слоя (описания колонок и метрик, glossary: «churn», «active user» и т.д.) → пополнение Golden Bucket (через ревью, §3.1).
- Каталог «известных ошибок» и исправлений SQL (например, частые ошибки диалекта) подмешивается в контекст.
- Любые изменения промптов и знаний проходят через eval (§3.6) до раскатки (regression gate, A/B или canary).
- [PROTO-lite] В прототипе system level показан через: журнал фидбека (`/good`, `/bad`) и ошибок SQL в логах; кандидатов в Golden Bucket с ревью (§3.1 п.5); отчёт `scripts/failure_report.py`, который группирует неудачные ходы по типу ошибки и выводит топ проблемных вопросов — вход для улучшения промптов и glossary.

### 3.5. Resilience & Graceful Error Handling [HLD] + [PROTO]

- [PROTO] **Self-correction SQL:**
  - распознавание синтаксических и семантических ошибок BigQuery (через dry-run до реального выполнения, это бесплатно) → ошибка передаётся LLM для исправления;
  - распознавание пустого результата → проверка гипотез (неверный фильтр, регистр, формат дат, несуществующее значение), например через запрос distinct-значений;
  - **лимит попыток** (например, 3) и бюджет токенов/байт на ход → после исчерпания понятное сообщение пользователю с объяснением и предложением переформулировать.
- [PROTO] **Контроль стоимости:** dry-run вместо реального прогона для валидации, кэш результатов идентичных запросов, кэш схемы, лимит `maximum_bytes_billed` на запрос **и** суммарный бюджет байт BigQuery на ход, ограничение числа LLM-вызовов на ход (max steps агента), сокращённые tool results в контексте.
- [PROTO] **Сбои внешних сервисов (Gemini, BigQuery):**
  - retry с exponential backoff + jitter на 429/5xx/timeout, с учётом `Retry-After`;
  - таймауты на каждый вызов;
  - fallback-модель (например, переключение на более лёгкую Gemini или другого провайдера при недоступности основной);
  - circuit breaker в HLD;
  - понятное сообщение при недоступности («BigQuery временно недоступен, попробуйте через минуту»), диалог при этом сохраняется.
- [PROTO] CLI **никогда не падает** с traceback: все исключения перехватываются на уровне хода, логируются с `trace_id`, пользователь получает дружелюбное сообщение. Ctrl+C и пустой ввод обрабатываются корректно.
- [PROTO] Учёт rate limits бесплатного Gemini API: клиентский rate limiter, экономия вызовов.
- [PROTO] Сбои вспомогательных сервисов не ломают ход: недоступность LangSmith (трейсы отправляются в фоне, ошибки только логируются), embeddings (fallback на keyword-поиск по Golden Bucket), guard-модели (только правила), post-turn извлечения контекста/предпочтений (ход завершается без обновления).
- [HLD] Очереди для долгих задач (генерация больших отчётов), идемпотентность, деградация функциональности (например, без Golden Bucket при его недоступности).

### 3.6. Quality Assurance [HLD] / [PROTO-lite]

- **Офлайн-eval до деплоя:**
  - golden-набор вопросов (из Golden Bucket и вручную) с эталонным SQL и ожидаемыми результатами;
  - метрики: execution accuracy (результат SQL совпадает с эталоном), валидность SQL, корректность выбора таблиц и метрик, faithfulness отчёта (цифры в тексте совпадают с данными), полнота ответа на intent, наличие action items в отчётах;
  - LLM-as-a-judge с рубрикой плюс выборочная ручная проверка аналитиками;
  - **security-набор:** red-teaming (prompt injection, извлечение PII, доступ к чужим продуктам, обход подтверждения удаления, off-topic); ожидаемый результат 100% отказов или блокировок;
  - регрессионный прогон в CI при изменении промптов, моделей или кода.
- **Проверка соответствия intent:** агент переформулирует понимание вопроса или допущения в отчёте, judge-модель сравнивает вопрос и отчёт, собирается обратная связь пользователей.
- **Оценка UX:** время до ответа (p50/p95), число уточняющих ходов, доля переформулировок, CSAT/👍👎, доля сохранённых отчётов, task completion, юзабилити-сессии с руководителями.
- [PROTO-lite] Скрипт eval (`evals/run_eval.py`) с кейсами по всем категориям сценариев §9, включая security и многоходовые:
  - детерминированные проверки (отказ, вызванные tools, отсутствие PII, ACL, формат ответа);
  - **execution accuracy:** для кейсов, построенных из golden trios, итоговые цифры ответа сверяются с результатом эталонного SQL;
  - **LLM-as-a-judge** (обязательно): рубрика «отвечает на intent», «цифры совпадают с данными», «есть action items», «соблюдён формат пользователя», оценка 1–5 с обоснованием;
  - итоговый отчёт (таблица + JSON) для сравнения версий промптов/моделей.
- [PROTO] unit-тесты на SQL Guard, ACL, PII-маскирование, confirmation flow, историю и предпочтения.

### 3.7. Observability [HLD] + [PROTO]

- [PROTO] **Трассировка:** у каждого хода есть `trace_id`/`conversation_id`. Логируется вся цепочка: вход пользователя → промпт → вызовы LLM (модель, токены, latency) → tool calls (аргументы и результаты) → SQL (текст, bytes processed, длительность, ошибка) → retries → финальный ответ.
- [PROTO] Структурированные JSON-логи в файл. Опционально интеграция с Langfuse / LangSmith / OpenTelemetry / Arize Phoenix. В HLD: Cloud Logging + Cloud Trace + Cloud Monitoring + BigQuery-sink для аналитики логов.
- [PROTO] Логи сами не содержат PII (маскирование перед записью).
- [PROTO] Инструмент разбора: CLI-команда `/trace <id>` восстанавливает шаги агента по trace_id, `/trace <id> --full` — полную переписку с моделью (сообщения, отправленные в LLM, и её ответы, уже маскированные). Полные payload'ы пишутся в отдельный `logs/llm_payloads.jsonl` (флаг `LOG_LLM_PAYLOADS`), чтобы основной лог оставался компактным. В LangSmith та же переписка видна в UI.
- [PROTO] `/stats` — метрики из списка ниже, посчитанные по логам, включая оценку стоимости (токены × цена из конфига).
- **Метрики уровня агента:**
  - доля успешных ходов и доля ошибок (по типам: LLM error, SQL syntax, empty result, timeout, guardrail block);
  - число self-correction попыток на ход, доля успешных исправлений;
  - latency (p50/p95/p99) по ходу и по компонентам;
  - токены и стоимость на ход/пользователя/день, bytes processed в BigQuery;
  - срабатывания guardrails (PII-маскирование, off-topic, injection, ACL);
  - метрики деструктивных операций: запрошено, подтверждено, отменено, истекло;
  - пользовательский фидбек (👍/👎), доля переформулировок;
  - доступность внешних сервисов, частота retries и fallback.
- [HLD] Алерты (рост доли ошибок, рост стоимости, недоступность Gemini/BQ), дашборды, семплирование трейсов для ручного ревью.

### 3.8. Agility: Persona Management [HLD] / [PROTO-lite]

- Инструкции агента (тон, стиль, структура отчётов, persona) хранятся **вне кода** и меняются без редеплоя.
- HLD: хранилище промптов с версионированием (Firestore / GCS / Langfuse Prompt Management / Vertex AI Prompt Management), простой UI для не-разработчиков (Admin UI, Google Sheet/Doc → sync или CMS), история версий, откат, предпросмотр, опционально обязательный eval-прогон перед публикацией.
- Агент подтягивает актуальную версию при старте каждой сессии или по TTL-кэшу (hot reload).
- Разделение промпта на **неизменяемое ядро** (безопасность, правила PII, правила подтверждения; не редактируется через persona) и **редактируемую persona** (тон, стиль), чтобы смена тона не могла ослабить guardrails.
- [PROTO-lite] `config/persona.md` — обычный текстовый файл, который может править не-разработчик. Перечитывается в начале каждого хода, перезапуск не нужен. Версия (хэш) persona пишется в трейс каждого хода.

### 3.9. История чата и контекст сессии [HLD] + [PROTO]

**Требование:** агент хранит историю разговора и понимает уточнения в контексте сессии («а для Women?», «а в прошлом году?», «покажи то же самое помесячно», «почему так?», «сделай из этого отчёт», «удали отчёт, который ты только что сохранил»).

- [PROTO] **Хранение истории:** вся переписка (сообщения пользователя, ответы агента, tool calls и их результаты) сохраняется в SQLite через LangGraph checkpointer (`SqliteSaver`). Ключ — `thread_id = conversation_id`. История переживает перезапуск CLI.
- [PROTO] **Продолжение разговора:** `/history` показывает список своих разговоров (дата, первый вопрос, число ходов), `/resume <id>` продолжает выбранный, `/new` начинает новый. Чужие разговоры недоступны: `conversation_id` привязан к `owner_user_id`.
- [PROTO] **Понимание уточнений:**
  - LLM получает историю сессии целиком (в пределах бюджета токенов), включая SQL и краткие результаты предыдущих ходов, поэтому может модифицировать предыдущий запрос, а не строить его заново;
  - в state хранится **контекст анализа** последнего хода: последний выполненный SQL, использованные метрики, период, фильтры и сущности. Он явно подаётся в промпт блоком «Current analysis context», чтобы короткие уточнения однозначно применялись к нему;
  - неоднозначное уточнение («а там?») → агент переспрашивает, а не угадывает;
  - отчёт можно собрать из результатов уже выполненных в сессии запросов без повторных запросов к BigQuery, если данных достаточно;
  - ссылки на объекты сессии («этот отчёт», «последний отчёт») разрешаются через сохранённые в state `report_id` текущего разговора.
- [PROTO] **Длинные разговоры:** при превышении бюджета контекста старые ходы сворачиваются в summary (LLM-суммаризация на лёгкой модели: ключевые вопросы, выводы, цифры, определения). Последние N ходов остаются дословно. Старые tool results сокращаются до SQL и сводки, полные таблицы не хранятся в промпте.
- [PROTO] **Учёт контекста во вспомогательных компонентах:** input guard и Golden retrieval работают не по последнему сообщению, а по нему вместе с предыдущими репликами пользователя. Иначе «а для Women?» будет ложно считаться off-topic и не найдёт похожие trios.
- [PROTO] **Безопасность истории:** в историю попадают только уже маскированные данные (tool results после PII-маскера; ввод пользователя прогоняется через `mask_text` перед сохранением). Контекст не обходит ACL: каждый SQL из уточнения снова проходит SQL Guard.
- [HLD] История хранится в Firestore / Cloud SQL с TTL (retention, например 90 дней), шифрованием и правом пользователя удалить свою историю; summary и контекст анализа хранятся рядом с thread.

## 5. Расширяемость [HLD] + [PROTO]

- [PROTO] Архитектура на основе **инструментов (tools) с единым интерфейсом и реестром**. Новая возможность (графики, отправка отчёта по email, веб-поиск трендов, экспорт в PDF/Slides) добавляется регистрацией нового tool без изменения ядра.
- [PROTO] Для каждого tool в реестре описываются схема входа/выхода, допустимые роли и флаги `side_effects` / `requires_confirmation`. Механизм подтверждения из §3.3 вынесен в общий helper и переиспользуется для любых действий с побочными эффектами (например, отправка email).
- [PROTO] Демонстрация расширяемости: tool `export_report(report_id)` (сохраняет отчёт в `exports/<id>.md`, помечен `requires_confirmation`) показывает, что новое действие с побочным эффектом подключается регистрацией в реестре и автоматически получает подтверждение, логирование и проверку прав.
- [HLD] Пошаговая инструкция «как добавить новый tool» в документации.
- Интерфейс (CLI) отделён от ядра агента, чтобы в HLD подключать Web/Slack/Teams без переписывания логики.
- [HLD] Описать, как подключаются: генерация графиков (matplotlib/Plotly → GCS → ссылка), отправка email (SendGrid/Gmail API, с подтверждением), веб-поиск (Google Search grounding / Tavily), MCP-серверы.

## 7. Архитектура

### 7.1. Компоненты прототипа (логически)
1. **CLI Interface:** REPL (`rich` + `prompt_toolkit`), команды `/help`, `/reports`, `/history`, `/resume`, `/new`, `/prefs`, `/good`, `/bad`, `/trace`, `/stats`, `/exit`, отображение таблиц и markdown, индикатор прогресса, обработка подтверждений.
2. **Session / Conversation Manager:** LangGraph checkpointer (история и state разговора), текущий пользователь, conversation_id.
3. **Input Guard:** классификатор тематики и prompt injection с учётом контекста разговора.
4. **Agent Orchestrator:** граф LangGraph, LLM (Gemini) + цикл tool calling с лимитом шагов, автоматическая подача golden trios в промпт.
5. **Tools (через реестр, §5):**
   - `describe_dataset`
   - `run_sql` (через SQL Guard → BigQueryRunner)
   - `get_company_benchmark` (обезличенные агрегаты по компании)
   - `save_report`, `list_reports`, `get_report`, `search_reports`, `request_report_deletion` (подтверждение через interrupt)
   - `export_report` (демонстрация расширяемости)
   - `update_user_preference`
6. **SQL Guard:** парсинг (sqlglot), read-only проверка, whitelist таблиц, PII-проекции, ACL-переписывание, LIMIT, dry-run и оценка стоимости.
7. **BigQuery Runner:** существующий `bq_client.py` с ретраями, таймаутами, `maximum_bytes_billed`, кэшем.
8. **PII Masker:** маскирование результатов (до LLM) и финального вывода.
9. **Confirmation Handler:** детерминированный обработчик pending actions.
10. **Stores:** SQLite (reports, user preferences и сигналы, conversations, audit log, checkpoints), persona (`.md`), Golden Bucket seed и кандидаты (JSON), пользователи и ACL (`users.yaml`).
11. **Observability:** JSON-логи + LangSmith, `/trace`, `/stats`.
12. **Resilience layer:** retry/backoff/fallback-обёртки для LLM и BQ.

### 7.2. Production HLD (предложение, обосновать в документации)
- **Клиенты:** CLI / Web / Slack → **API Gateway / Load Balancer** + **Identity (IAP / Google Identity / Okta SSO)**.
- **Compute:** Cloud Run (stateless agent service, автоскейлинг); Cloud Run Jobs / Cloud Functions для фоновых задач (индексация Golden Bucket, извлечение предпочтений, eval).
- **LLM:** Gemini через Vertex AI (enterprise SLA, VPC-SC, квоты) плюс fallback-модель.
- **Данные:** BigQuery (read-only, row-level security, policy tags для PII, authorized views); GCS (Golden Bucket raw, артефакты отчётов); Vector store (Vertex AI Vector Search / BigQuery Vector Search / AlloyDB pgvector); Firestore или Cloud SQL (отчёты, сессии, предпочтения, pending actions, persona/prompt versions); Memorystore/Redis (кэш, rate limiting, сессии).
- **Безопасность:** Secret Manager, Cloud DLP, IAM с минимальными правами, VPC-SC, audit logs.
- **Асинхронность:** Pub/Sub (события фидбека, новые trios, генерация отчётов).
- **Observability:** Cloud Logging / Trace / Monitoring + Langfuse (LLM-трейсы, eval, prompt management) + BigQuery log sink + алерты.
- **CI/CD:** GitHub Actions / Cloud Build, eval-gate перед деплоем, canary.
- **Admin UI:** редактирование persona и ревью Golden Bucket candidates.

### 7.3. Обязательные диаграммы (Mermaid)
1. Общая архитектура (компоненты, сервисы, хранилища, compute).
2. Sequence-диаграмма обработки вопроса (guard → retrieval → SQL → self-correction → masking → ответ).
3. Sequence-диаграмма деструктивной операции (prepare → preview → confirm → execute / cancel).
4. Learning loop (пользовательский и системный уровни, обновление Golden Bucket).
5. Схема observability и data flow PII (где PII есть, где маскируется, куда не попадает).
6. Прототип vs production: какой компонент прототипа каким сервисом заменяется.

Кроме диаграмм, в документации обязательны:
- таблица **хранения данных**: какие данные, где хранятся (прототип / production), кто имеет доступ, retention, есть ли PII;
- описание **взаимодействия компонентов**: синхронные вызовы (HTTP/gRPC к Cloud Run, Vertex AI, BigQuery API) и асинхронные (Pub/Sub для фидбека, сигналов предпочтений, кандидатов Golden Bucket, индексации), форматы сообщений.

## 12. Принятые решения (обязательны к реализации)

Эти решения имеют приоритет над вариантами «или / опционально» в разделах выше. Принцип: везде берём самое простое решение, которое закрывает требование.

### 12.1. Доступ к данным
| # | Решение |
|---|---|
| D1 | **Доступ по департаменту**: `products.department`. В thelook это `Men` / `Women`. Каждому пользователю системы назначается список департаментов |
| D2 | **Данные вне доступа:** разрешены только **обезличенные агрегаты по всей компании** (total revenue, orders, AOV, users, помесячная динамика) **без разбивки** по чужим департаментам, продуктам, брендам и клиентам. Детальные запросы работают только по своим департаментам |
| D3 | **Роли `ceo` и `c_level`** имеют полный доступ ко всем департаментам, ACL-фильтр не применяется |
| D4 | **Пользователи** заданы в `config/users.yaml` (`user_id`, `name`, `role`, `departments`). В CLI пользователь выбирается флагом `--user <user_id>`; без флага показывается список для выбора. Пароля нет, это имитация аутентификации. Демо-пользователи: `ceo` (all), `cfo` (c_level, all), `head_men` (Men), `head_women` (Women) |

**Реализация ACL (D1–D3), простой вариант:**
- Основной инструмент `run_sql` **всегда** пропускает запрос через SQL Guard. Для ограниченных ролей Guard через `sqlglot` подменяет каждую ссылку на таблицу отфильтрованным подзапросом:
  - `products` → `(SELECT * FROM products WHERE department IN (...))`
  - `order_items` → только позиции с `product_id` из разрешённых продуктов
  - `orders` → только заказы, в которых есть разрешённые позиции
  - `users` → только пользователи, которые покупали разрешённые продукты

  Поэтому LLM не может обойти фильтр формулировкой запроса: любые его SQL физически видят только «свои» строки.
- Для D2 есть отдельный инструмент `get_company_benchmark(metric, period)` с **фиксированными** параметризованными SQL-шаблонами (LLM не пишет SQL). Он возвращает только итоговые числа по всей компании. Так пользователь может сравнить «мой департамент vs компания в целом», но не видит детализацию по чужим.

### 12.2. PII
| # | Решение |
|---|---|
| D5 | PII-поля по умолчанию (практика GDPR/CCPA для прямых идентификаторов и точной геолокации): `users.first_name`, `last_name`, `email`, `street_address`, `postal_code`, `latitude`, `longitude`, `user_geom`. **Не PII:** `user_id`, `age`, `gender`, `city`, `state`, `country`, `traffic_source`. Список хранится в `config/pii_policy.yaml`. *Остаётся открытым вопросом к заказчику (§13)* |
| D6 | PII **можно использовать внутри SQL** (`JOIN`, `WHERE`, `COUNT(DISTINCT email)`), но PII **нигде не сохраняется**: не выводится пользователю, не передаётся в LLM в результатах, не пишется в логи, LangSmith-трейсы, кэш и отчёты |
| D7 | Защита от реидентификации через малые выборки (k-anonymity) **не нужна** |
| D8 | Конкретных клиентов показываем **по `user_id`** (`Customer #12345`) |

Следствия D6 для реализации:
- SQL Guard запрещает PII-колонки в **итоговой проекции** запроса (в том числе через `SELECT *`, алиасы и выражения вроде `CONCAT(first_name, ...)`). Если запрос нарушает правило, LLM получает ошибку и переписывает его.
- Второй слой: результат запроса до передачи в LLM проходит через маскер по именам колонок и regex (email, телефон). Так в LangSmith и логи PII не попадёт, даже если первый слой что-то пропустит.
- Третий слой: финальный ответ пользователю проходит через тот же regex-маскер.
- Литералы PII в тексте SQL (например, `WHERE email = 'john@...'`) маскируются перед записью SQL в логи и трейсы.

### 12.3. Деструктивные операции и отчёты (дефолты)
| # | Решение |
|---|---|
| D9 | Отчёт — это только **явно сохранённый** документ. Сохранение по просьбе пользователя или после предложения агента («Сохранить этот отчёт?») |
| D10 | «Client X» — любая сущность из текста отчёта: бренд, продукт, департамент, клиент по `user_id`. Поиск ведётся по `title` + `content` (SQLite `LIKE`, без FTS) и по полю `entities`, которое LLM заполняет при сохранении |
| D11 | Удаление soft (`deleted_at`) с записью в таблицу `audit_log`. Undo не делаем |
| D12 | Подтверждение в CLI: показать список → `Delete N reports? [y/N]`. Принимается только `y`/`yes`, всё остальное считается отменой. Усиленного подтверждения не делаем. Pending action живёт до следующего ввода пользователя |
| D13 | Шаринга отчётов нет, каждый видит и удаляет только свои. CEO тоже не удаляет чужие |
| D14 | Формат отчёта: markdown в SQLite. Экспорт не делаем |

### 12.4. Остальные дефолты
| # | Решение |
|---|---|
| D15 | **Golden Bucket:** синтетический seed из 10–15 trios в `data/golden_trios.json`. Retrieval: embeddings Gemini, cosine similarity in-memory (`numpy`), top-3 добавляются в промпт как примеры. Embeddings кэшируются в файл, чтобы не тратить квоту при каждом старте. Обновление в прототипе — кандидаты по `/good` + скрипт ревью (§3.1 п.5); полный пайплайн в HLD |
| D16 | **Адаптация под пользователя (полностью в прототипе, §3.4.1):** явные предпочтения через `update_user_preference`, неявные — по сигналам после каждого хода с порогом уверенности. Хранение в SQLite, подача в system prompt каждого хода, управление через `/prefs`. System-level learning описывается в HLD |
| D17 | **Persona (lite):** `config/persona.md` перечитывается в начале каждого хода, без перезапуска. Действует глобально; предпочтения пользователя имеют приоритет по формату, persona задаёт тон. Guardrails лежат в неизменяемом ядре промпта в коде |
| D18 | **LLM** (выбрано на шаге 0, ноябрь 2026): основная `gemini-3.8-flash`, fallback `gemini-3.5-flash-lite`, вспомогательные вызовы (input guard, извлечение контекста и предпочтений, суммаризация, judge в eval) — `gemini-3.5-flash-lite`, embeddings — `gemini-embedding-001`. Всё задаётся в `.env`. Free tier (не гарантирован Google): Flash ≈ 5 RPM / 20 RPD, Flash-Lite ≈ 15 RPM / 500 RPD, квоты считаются отдельно по моделям. Поэтому: вспомогательные вызовы не тратят квоту Flash; при дневном 429 на Flash — немедленный переход на fallback без ретраев; в README — совет переключить `GEMINI_MODEL` на Flash-Lite для free key. Для HLD: Gemini через Vertex AI |
| D19 | **Масштаб и SLA для HLD** (допущение): до 200 руководителей, до 20 одновременных сессий, ответ на простой вопрос p95 ≤ 20 с, доступность 99.5% |
| D20 | **Окружение проверки:** проверяющий использует свой GCP-проект для billing BigQuery (`GOOGLE_CLOUD_PROJECT`) и свой ключ AI Studio. В README есть пошаговая инструкция |
| D21 | Язык ответа совпадает с языком вопроса, основной язык английский |
| D22 | Графиков в прототипе нет; они описываются в HLD как пример расширения |
| D23 | История чата хранится в SQLite (LangGraph `SqliteSaver`) и переживает перезапуск; разговор можно продолжить через `/resume`. Уточнения понимаются в контексте сессии (§3.9) |
| D24 | Бизнес-метрики (churn, active user и т.п.): определения в `config/glossary.yaml`. Агент явно пишет в ответе, какое определение использовал |
| D25 | «Текущая дата» для относительных периодов — **системная дата**. Если данных за период нет, агент сообщает об этом и показывает доступный диапазон дат |

### 12.5. Технические решения
| # | Решение |
|---|---|
| T1 | **Фреймворк: LangGraph.** Причина: явный граф состояний подходит для guard → agent → tools → confirmation; есть checkpointer и interrupt (human-in-the-loop) для подтверждения удаления; нативная интеграция с LangSmith. Опыт: уже использовал в работе (уровень указать в README) |
| T2 | **LLM-провайдер:** Gemini (см. D18) через `langchain-google-genai` |
| T3 | **Хранилище:** SQLite (`data/app.db`): `reports`, `user_preferences`, `preference_signals`, `conversations`, `audit_log` + checkpointer LangGraph (история сообщений). Golden Bucket: JSON + in-memory embeddings |
| T4 | **ACL:** переписывание SQL через `sqlglot` (§12.1). Это значит, что Guard сам подставляет фильтр по департаменту в любой запрос LLM. Альтернатива «отклонять запросы без нужного WHERE» хуже: LLM будет часто ошибаться, а это лишние ретраи и стоимость |
| T5 | **Observability:** LangSmith (трейсы графа, LLM-вызовы, tool calls, токены, latency; проверяющий подключает свой `LANGSMITH_API_KEY`) + локальные JSON-логи (`logs/agent.jsonl`) с `trace_id` и CLI-команда `/trace <id>`. Если ключа LangSmith нет, всё работает на локальных логах |
| T6 | **Все lite-реализации делаются** (времени достаточно). Порядок — по `PLAN.md` |
| T7 | **Установка:** `src`-layout + `pyproject.toml`; `requirements.txt` содержит зависимости и строку `-e .`, поэтому `pip install -r requirements.txt` из задания сразу делает пакет запускаемым (`python -m retail_agent`) |
